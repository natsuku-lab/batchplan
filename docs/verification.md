# Verification

What the test suite pins down, so you know what to rely on.

`BATCHPLAN_REQUIRE_GPU=1 cargo test --release` runs every test, including the code in these guides, which compiles as doctests. `--features lerobot` adds the export tests and the README's and training-data guide's code, `--features usd` the OpenUSD tests, and `--no-default-features` runs the CPU-only build's. All configurations pass on a Ryzen AI Max+ 395 with a Radeon 8060S (Vulkan) and on an M4 Pro (Metal); CI runs them on Linux with the kernels on Mesa's llvmpipe. Earlier versions also passed on an NVIDIA T4 (Vulkan).

## Devices agree

- **Clearances:** over 20,000 configurations, GPU and CPU clearances agree to 3e-7 m, and gradients to 3e-4 relative.
- **IK:** GPU and CPU IK agree on all 4,096 seeds. On each, an IK step moves a seed by more than 1e-6 rad or leaves it exactly at rest.
- **Plans:** every GPU plan reported valid is re-checked on the CPU at 4× denser interpolation, and none penetrates.
- **Input checks:** malformed batches (wrong array lengths, a world index past the end, worlds uploaded to another device) are an `Err` on both devices. Each options type's `check()` returns the input error its call returns for those options, on every device, and passes the defaults, IK without steps, a rotation tolerance of infinity and smoothing switched off. `ik::failures` refuses the options `solve_ik` does; `evaluate` refuses weights that are not finite but takes an infinite margin without a weight; `servo` refuses a `slow_within` that is not a number. A batch past what 32 bits count (problems times seeds, and a plan's pose goals times the sixteen times their seeds its IK may come to try) is refused before anything is allocated. A time budget of `Duration::MAX` is no deadline for a plan's goal IK, search or optimization. A plan's search with no limit on its samples searches again without its clearance as one with a limit does.
- **Batches:** a problem's IK solves bit for bit alike alone and in a batch (on a GPU, on the same side of its lane switch), and its plan, optimization seeds included, alike anywhere in its batch. A pick's motions by a grasp are the same alone as among other grasps. Problems that differ start IK from random seeds of their own, and a problem given twice from the same ones. Plans keep the worlds of their problems when one world holds several targets, and obstacle-free worlds plan on both devices.
- **Warm-up:** warmed up or not, each device plans and solves IK alike. Warming up a GPU device builds its constrained trajectory kernels and its grid kernels.

## Collision

- **Obstacle distances:** every obstacle kind returns unit gradients that match finite differences, stepping back along the gradient lands on the surface, and cylinder and capsule distances match closed forms. The GPU agrees with the CPU for each kind. Collision gradients match finite differences.
- **SIMD lanes:** lanes checking eight configurations at a time give the same world and self clearances as the scalar twin of the GPU kernels, to 2e-5 m, over 3,000 random configurations against every obstacle kind, on the Panda (fingers locked or sliding), the Panda holding a box, MuJoCo Menagerie's 2F-85 (quartic mimic joints) and the UR5e. Runs of worlds cross the groups of eight. Their yes-or-no check (`keeps`) of a 1 cm margin, and of links kept 1 cm apart as splines keep them, agrees with the scalar twin's exact clearances away from the boundary, at the CPU's best SIMD level and at the baseline.
- **Allowed contacts:** on every device, a bar through the open fingers collides until the world lets the hand touch it; letting one finger touch it leaves the other colliding, and links the world does not name still collide. IK solves a grasp inside an object, and a plan reaches it, only with the touch, and `MeshModel` skips the same pairs. A held box rests on a table only on the holder's device, where the world may name it. Unknown links and obstacle indices are input errors on every device and in `MeshModel`. The lanes match the scalar twin on worlds with touches, and the GPU matches the CPU with touch sets that span several words. Worlds uploaded for the robot without the objects it holds give the robot holding them the same clearances as worlds uploaded for it. Removing an obstacle takes its touches with it and renumbers the rest.
- **Rotations:** a rotation a thousandth off a unit quaternion turns what it places as the unit one does, while a unit rotation's frame is its matrix to the bit. A long box, cylinder, capsule and grid so turned measure the same and give 300 configurations the same clearance and cost on every device; held shapes keep within the tolerance of where the unit rotation places them, a grasp holds its object in the same place, a part stands where its base puts it, and the mesh checks read the same distances. A camera so turned builds the same grid and map and marks the same readings, but for a few grid points that project into a neighbouring pixel. A camera's pose and a part's base that are not finite with a unit rotation are refused.
- **Mesh clearances:** distances to every obstacle kind match closed forms to 0.1 mm, follow the joints, stay exact among several obstacles in any order, and read zero across a surface. Self clearance between links matches too, and a concave link is measured on its surface, not its hull. Against a grid of a cube, clearance stays within the grid's documented slack. Held objects are checked as part of the robot, and the Panda's meshes load and read clear of its own table. Fitted spheres never read farther than the meshes over 300 random configurations.

## Distance grids

- **Gradients:** gradients match finite differences inside the grid and beyond its box, away from cell faces; so do collision gradients through a grid.
- **Devices:** the GPU agrees with the CPU to 3e-7 m (Metal and RADV), including two grids in one world, one of them shared with another world and stored after a grid with an odd number of points.
- **Mesh and point grids:** mesh grids never read farther than the true distance and at most a voxel diagonal nearer, outside the solid and inside a single shell; inside a solid of several shells they read solid, as deep as the nearest face. Point grids never read beyond their solid voxels. Open and non-manifold meshes are refused.
- **Solids of several shells:** a mesh of several shells is the solid they wind around: a leg that runs up into its top, an inward-facing leg, a cavity facing either way and a corner pushed through the opposite face read solid and free where that solid is. In a cube with an off-centre cavity, a box turned about every axis, a prism and a ball of 9,000 facets, every point reads its distance to the surface less half a voxel diagonal. The ball, crossed on several threads, gives the same grid to the bit with its faces turned in.
- **Ruled out by its box:** a grid is ruled out by its box for a link far from it. Over 6,000 configurations around a grid whose ball is larger than its box and a solid one turned by a quaternion that is not unit, clearances and costs match checking every sphere, on every device, and the least value on a grid's faces is found on every face.

## Planning

- **Trajectory optimization:** the first L-BFGS step has no history, so it is steepest descent. Its direction, scaled to its largest entry, matches finite differences of the smoothness cost and of the full cost (smoothness plus collision sampled along the spline) on every device. On reaches whose straight line a ball blocks, GPU and CPU step directions agree to 5e-5 at the first step and to 4e-4 at the fourth, and both devices lower the full trajectory cost alike. The two-loop recursion equals an explicitly built BFGS inverse Hessian, and a line search that finds nothing cheaper resets the history.
- **Optimization seeds:** with no steps taken, a problem's first two seeds are its searched spline and the straight line to its goal. A problem searched to its straight line is not optimized, and a budget spent while searching starts no optimization. Plans without seeds do not depend on the optimization's weights.
- **Edge checks:** on every device, 400 queries over random edges (how many edges from the first are free, or which is the first free one) get the same answers as checking every state one by one, and CPU and GPU answers are identical. An edge 5–10 mm from an obstacle is free, fails to keep a 1 cm clearance, and keeps it where its ends are near the path's ends.
- **RRT-Connect:** every edge it returns is collision-free under a CPU check four times denser, on both devices. Paths start at the start and end at a goal, and only straight or bent lines (at most four waypoints) have edges longer than the range. A straight line blocked halfway by a small ball is bent around it, with at most four waypoints and within 10% of the straight length. With a 20 cm ball where the hand passes halfway along the straight line, 48 random Panda reaches plan paths under 5.5% longer than straight on average, at most five of them more than 10% longer. Where no spline follows the path found near the straight line, as in MotionBenchMaker's `bookshelf_tall_panda` problem 1, the problem is searched again over the joint ranges and solved. Fixed seeds give identical paths; changing the seed changes them.
- **Search internals:** as a tree grows to 3,000 nodes, the k-d tree finds exactly the node and distance a scan of all nodes finds, taking the lowest node among equals. A search helped by other threads grows the same trees, node for node and bit for bit, as it grows alone, with a clearance and without, in a batch and alone. Searched again on the same helpers' state, it is helped from its own first samples.
- **Splines:** splines pass through the path's ends and every pinned waypoint, run along the path when every waypoint is pinned, and spread their control points evenly along it when none is. They double their control points while fewer are free than the longer of a problem's two paths has waypoints. A blended pin draws the curve in around its corner without stopping it; only an exact pin stops it there. Splines are checked at samples no farther apart than the edge resolution, however long a span, and after a change a check starts no later than the first sample that changed. Across 512 pick-and-place tasks with a wall, posts, an arch or a cluster of boxes across the carry, the arm never touches the scene, and at most 20 carries stop on their way.
- **Shortcutting:** shortcutting never lengthens a path or moves its ends, and every new edge passes the same denser check. On a detour over a ball, with the wrist turned 1.5 rad out and back, straightening leaves the wrist with no turn and the path clear.
- **`plan`:** `plan` solves every UR5e problem RRT-Connect can reach (at least 20 of 24 far reaches), its timed plans clear the CPU check, and the CPU and the GPU plan identically. Continuous joints turn the short way, the long way round only when the short way is blocked, and RRT-Connect finds the way through π. CPU IK solves targets taken from collision-free configurations.
- **Several hands:** two UR5e arms assemble into one 12-joint robot with two hands on disjoint joints, each hand where the arm alone puts it. IK toward both hands' targets at once solves at least 28 of 32 problems on every device, each hand within tolerance and the arms clear of each other; with only one hand targeted, every seed leaves the other arm exactly where the seed has it. From a configuration at both targets, the collision push moves neither hand by more than the damping lets through. Hands that share joints, the Panda's hand and its fourth link, solve together: 32 of 32 problems at the default iterations on every device; their collision push moves neither hand, and one step of 0.3 rad matches the CPU's to 5e-5 rad on the GPU. Reach demonstrations refuse a goal that targets only the second hand with an input error.
- **Held joints:** joints a problem holds (`IkProblem::hold`) stay bit for bit where its seed has them in every seed on every device, and 32 of 32 problems reaching poses with them there solve, with one hand and with two hands sharing them; holding a joint the robot lacks is an input error. With the right arm held, RRT-Connect carries the left hand over a wall and every waypoint keeps the right arm where it starts. Plans with optimized seeds keep it in every control point of every valid seed and, up to rounding, in every timed sample, on every device. No direction a bend can take moves a held joint, and no goal variant a turn away turns one.

## Constraints

- **Kept along the path:** a gripper carried upright past a pillar, within 5°, keeps the bound at 1 kHz along every valid path, searched or optimized, and is collision-free, on the CPU and the GPU. A hand kept in a box, its tilt and its twist bounded, keeps all three. An arm carries upright while the other arm's joints keep their values bit for bit. Every timed constrained path passes `Trajectory::check`, and a spline fitted through a path that starts at a joint's limit keeps its control points within the joint's range.
- **Relative to another hand:** two arms carry a tray level over a block, the right hand pinned in the left hand's frame: every path keeps the right hand within 2 mm and 0.02 rad of its place at 1 kHz and the left within 5° of straight down. The carries average within 1.14 times the unconstrained paths' length. A goal 1.5 mm off its place plans; one 4 mm off is an input error.
- **Seeds and splines:** optimized seeds that break their constraints are invalid, and every seed still valid keeps them. Splines of 10 control points too short to follow a 1° bound are repaired within it, and every reach under 4 rad plans with 10. With 7 control points, one free, every two-arm tray carry plans with more, keeping its bounds at 1 kHz and collision-free, while its optimized seeds keep 7. A problem whose spline grew is optimized even within 2% of its straight line.
- **Checks:** `Robot::breach` tests a state as `plan` tests its ends: a hand turned past a twist bound breaks it, and a bound below IK's precision counts as that precision. Validation refuses a path that breaks its constraints between its ends. Ends that break their constraints, a hand the robot lacks, a constraint relative to its own hand or a missing one, a negative bound and a bounded twist without a tilt bound are input errors that say what was wrong, through `plan`, `join` and the tasks; a task names itself.
- **Through compositions:** blends keep a sequence's constraints. A place carries the box upright over a wall it would otherwise tip it past, a pose reached tilted stops at the transit, the pose behind it gets its own transit, and a pick whose hand must stay near its start stops at the transit too. A follower's replan around a box keeps the gripper upright; kept near its goal, where it is not yet, it stops instead of replanning; and a trajectory whose goal breaks the follower's constraints is an input error.
- **Same everywhere:** the same constrained problems plan identically alone, in a batch with unconstrained ones, and on either device, and another sampling seed changes some of them.
- **Inside:** the lanes judge constraints exactly as the scalar test does on states that keep and break each kind of bound, in the world and relative to another hand, at the best SIMD level and the baseline. Each projection row changes at the rate the Jacobians of both hands give, and the optimizer's cost at the rate of its gradient. The GPU's optimization steps match the CPU's on constrained problems within 1e-3 of their largest entry at the first step and 1e-2 at the second, and the two-arm carries within 1e-2 at the fourth. On a hand pinned in the other's frame, a spline fitted through waypoints whose edges leave the bounds keeps them at every free control point's knot, and a shortcut's walk keeps them at every hop's middle.

## Trajectories and timing

- **Limits:** planned trajectories stay within velocity, acceleration and jerk limits along their whole length, reach the binding limit, and start and end exactly at rest. Retiming keeps the endpoints. The analytic velocity and acceleration match finite differences. A trajectory starts and ends at its first and last control points, exactly.
- **`at` and `check`:** `at` makes no allocations. `check` refuses a NaN, running too fast, a jerk spike, a moving start, leaving a joint range and the wrong joint count. It measures a joint's range on the curve itself, span by span, so a moving start's first control point, which lies behind the start, does not count.
- **Scaled limits:** a robot loaded with its velocity, acceleration and jerk limits scaled by 1/2, 1/4 and 1/8 has exactly those limits and times every planned path at twice the duration, within them. A scale outside (0, 1] fails to load.
- **Stops:** planned full-speed reaches are stopped 20% and 50% of the way through. At least 20 of 24 stops start in exactly the state they leave, keep every limit, stay on the path, come to rest, and take less time than going on; in the rest, the path ends first. A trajectory at rest stops where it is, and a stop starts where it was called and ends short of the path's end. Of states with a joint at its velocity limit, at least a quarter stop before the motion brakes for its own end; of stops asked through a motion's first fifth, at most a tenth are refused and at most one in fifty takes longer than going on.
- **Moving starts:** `check_from` takes a start whose velocities and accelerations are within 1e-4 of their value plus each joint's limit, and refuses one a hundredth of an acceleration limit off. Of reaches replanned to their own goals partway through at full speed (a joint above 1.5 rad/s), at least nine in ten succeed on each device, each timed from exactly the state it starts in. Motions replanned to new goals from halfway along, at about 3 rad/s, take less than three times as long as the same moves from rest, and under 1.845 times on average, and start in exactly the state they leave. A replanned motion's timing, sampled 4,000 times, stays under 1.001 times every acceleration and jerk limit. Replanned from 30%, 50% and 70% of the way along, on the Panda and the SO-101, every path `plan` returns is timed from exactly that state and passes `check_from`.
- **Hand speed caps:** under caps at half the hand's speed and turn rate with the joints' limits alone, each alone and both, planned trajectories keep the caps, come within 10% of one, and take on average under 1.35 times what the hand's travel and turn need at them. A straight 10 cm tool path at 5 cm/s takes between 2 and 2.3 s. A hand with neither cap is timed exactly as the joints alone allow. Bad caps and hands are input errors.
- **Followers:** a follower given a measured state 0.1 rad short of its trajectory goes on as it was; given one held a third of the motion back, it re-anchors there, from its position and velocity, and arrives at the goal. Held inside a box, where no plan starts, it holds the robot there, blocked, and a measured state of the wrong size is refused. A replan's status hands over the trajectory that takes over at its time, while the old one runs until then; with a lead, the takeover comes `budget + lead` after the tick that replans. A negative or NaN lead is refused.

## Why requests fail

- **Contacts:** `Device::contacts` lists what 2,000 random Panda configurations come within 5 cm of, on every device: its nearest world and self contacts equal `evaluate`'s exact clearances, nearest first, and both devices list the same. A table the world lets every link touch, and a table under the base, which no joint moves, name no contact. A configuration that is not finite is an input error to `evaluate` and to `contacts`. `contacts_holding` lists, for configurations holding nothing, a cube and a bar in one call, what a device built by attaching each object lists, in the items' order, nothing where the world lets the held object rest, and what `contacts` lists where nothing is held. Holds that are not one per item, a hold the robot cannot take and a configuration that is not finite are input errors naming their item.
- **Plans:** on every device, a plan whose start is boxed around the hand fails as `StartCollides`, and one whose goal is, as `GoalCollides`, each naming `panda_hand` in the box; a free reach has no failure. A search that may not sample fails as `NoPath` and nothing else, no time at all as `OutOfTime`, and a slowed Panda moving too fast toward a ball to brake as `NoSpline`.
- **IK:** `ik::failures` calls a pose 2 m away `Unreachable` and a pose boxed around the hand `Collides`, naming the hand. It solves again without the push away from obstacles before calling a target out of reach: among 200 targets with balls in the hand's way, more than five are reached only that way.
- **Motions and tasks:** a stopped straight move names what its next step collides with, and nothing for a pose out of reach. Every stopped task candidate names what it collides with (the slab over the grasp, the block over the approach, the box around the start), and a place that may not touch the table names the held object on it.

## Tool paths

- **Precision:** on every device, a 10 cm straight move stays within 1 mm and 0.01 rad of the line, and ends at its pose. A turn in place keeps the hand where it is. An L-shaped path keeps its precision through the corner at 5 mm steps and at 5 cm ones. CPU and GPU devices return the same motions.
- **Stops:** a slab across the way stops the motion between a tenth and three fifths of the way down, as a `Collision`, and what it returns keeps clear of the slab. A pose out of reach stops it as `Unreachable` after a straight stretch. A move across the UR5e's wrist singularity stops short of it with 300 IK iterations and passes it with 1,000, the hand on the line throughout. An approach that ends around a bar succeeds only where the hand may touch it.
- **Limits:** from 400 starts near the Panda's joint limits, every motion keeps the limits along its whole spline. In 200 random pours (up to a radian of turn over half a millimetre to six), the motions stop on the way in at most one in fifty and keep the precision. A start past the limits, malformed paths and malformed options are input errors.
- **Screws (`Screw::path`):** a frame 10 cm from an upright line, carried a quarter turn, ends where trigonometry puts it; every waypoint keeps its distance from the line and its height, and the straight moves between them sag from the circle by at most the precision. With a pitch, each waypoint is as far along the line as its share of the turn. A Panda's hand following the waypoints 10 cm from a hinge keeps within 1 mm of the arc on every device. A screw that is not finite or not unit, an angle that is not finite, a precision not above 0, and a turn that would take more waypoints than can be held are input errors that name the values.

## Tasks

- **Picks:** on every device, a post where a finger of either grasp from above closing along the box goes stops both, and the third gets through alone: its motions joined and within the limits, its approach ending at the grasp and its departure lifted by `lift`. Without the post all three come back, quickest first; each alone moves exactly alike. A box as wide as the fingers open is picked only because they may touch it, and a grasp set deeper than the fingers reach below the palm is refused.
- **Where a task stops:** each step is shown stopping a task, with its reason: a slab where the palm would be stops every grasp at `Reach` as colliding, a box beyond reach at `Reach` as out of reach, a block over the box the moves in (a move in shortened by `min_fraction` gets through), a lid just over the box and a table that is not its support the lifts, and a start inside a box `Start`. The message counts each. The contacts name each obstacle as the task's world numbers it, and a place backing off from a box it holds names the box after the world's obstacles.
- **Places:** a picked box is set down at the second of two poses, the first taken by another box: the hand lowers it along `lower`, lets go at the grasp and backs off along its z axis. Without the table as its support it cannot be let go of there. One place task per grasp a pick came back with plans every one, and a held object sits in the hand where its grasp holds it, for grasps that are not their own inverse.
- **Two arms (`Place::idle`):** of two Pandas, the left sets its box down while the right waits where the start has it, or turns away on the transit and waits there through the moves in and away; the left arm's joints in that configuration do not count.
- **Each step's world:** six picks and six places in one call each, over three worlds that differ only in what the hand may touch, stop at the step whose world forbids a touch and name the obstacle. A task without its transit gives the moves of the same task with it, candidate by candidate.
- **Fingers per grasp (`Hold::locked`):** beside a post the open fingers come down on, a pick with its fingers 2 cm apart plans as it does alone on a device for the robot relocked so, and its hold says where the fingers are. Grasps with fingers of their own are numbered as the pick's grasps are, and their stops come back in the pick's order. A joint that was not locked is an input error naming the task.
- **Opening at release (`Place::open`):** between two posts 3 cm off a box's sides, a place that names no opening stops at its release, the fingers as loaded on the posts. One that names four lets go at the first of them clear of the posts there, says which, and backs off the `retreat`. Places that name openings and one that names none plan alike in one call. An opening naming an arm's joint is an input error naming the task and the opening. A release the arm cannot reach names the block it meets, the fingers where they hold the box.
- **Enough plans (`Pick::enough`, `Place::enough`):** of a hundred grasps or releases of which four get through, one, two and ten plans that will do give the first one, the first two and all four in their order, each as the task that tries every candidate plans it, on every device. In one call, tasks that want different counts each get theirs. A task none gets through says where each of the hundred stopped, as without a count; among grasps with fingers of their own the first that plans is taken; and no plans being enough is an input error naming the task.
- **Costs (`Hold::cost`, `Release::cost`):** every cost alike gives the plans and their order costs of 0 give, the quickest first and those as quick in the grasps' order. A grasp costing least comes first, the rest quickest first. With two plans that will do, they are the first two in the grasps' order to get through, the cheaper first, whatever a later grasp costs. A cost that is not finite is an input error naming the grasp. Holds costing their grasps' `unseen_span` pick those closing on two seen patches first, then the one-sided by their span. A place that wants one plan tries its releases in their order whatever they cost.
- **Held objects:** a held object collides where its grasp holds it: in one call with a cube taken from above, a 30 cm bar taken from the side near its foot lifts into a slab over its top, and taken near its top clears a higher slab. Each object is fitted once and placed by each grasp. The devices `pick` and `place` hold objects on have the collision model `Held::attachment` gives. A place of an object whose size is not finite is an input error.
- **A held object per problem:** one `plan`, `solve_ik` or `follow` call over problems holding nothing, a cube by two grasps and a bar, interleaved, gives each problem what a device holding its object alone gives, on each device, plans with optimized seeds included. Holding the cube, a goal over a slab collides, an IK target there fails naming the held link, and a tool path down to it stops on the slab, where the hand alone gets through. A hold the device cannot take (one it holds already, a hand it lacks, a distance grid, a grasp that is not a pose, worlds whose touches were resolved for a robot holding in the other hand) and an IK problem's world out of range are input errors naming their problem, however the batch is grouped. Devices on one GPU or thread pool fit a held object once and keep the latest 64, the least recently used going first.
- **Held by two hands (`Held::also`):** two Pandas hold a 32 cm bar from above, 24 cm apart. IK given the left hand's pose puts the right at its grasp within 2 mm and 0.02 rad, on every device; held by the left alone, the bar collides with the right hand there. Plans given the left hand's goal pose alone carry it over a block: at 1 kHz every path keeps the right hand within 2 mm and 0.02 rad of its grasp and is collision-free with the bar, where the same ends planned holding nothing pull the hands centimeters apart. A join's blend that pulls them apart holding nothing keeps them holding it. A follower refuses a trajectory whose goal has a hand off the bar. A straight move of either hand that lifts the bar 15 cm and turns it 0.3 rad keeps the right hand within the path's precisions of its grasp at every step and within 2 mm and 0.02 rad at 1 kHz, where the same path holding nothing leaves the right hand behind, and a plan holding the bar starts where it ends; a half radian turn of the left hand in one step is split until the right hand keeps to 0.2 mm, where holding nothing it takes one step, and with the right arm's joints held the motion stops at the start. Two hands pick the bar up off the block by pairs of their grasps from above, every pair getting through on every device: each plan's candidate is its pair's index, its cost the sum and its hold both grasps' fingers; at 1 kHz the left hand moves in while the right waits, then the right while the left waits at its grasp, both under the tool speed and both ending at their grasps; the lift raises the right hand with the left, within 2 mm and 0.02 rad of its grasp and clear of everything holding the bar; and one or two plans that will do are the first pairs in the given order, as trying every pair gives them. Setting the bar down 4 cm along the block, the transit and the lower keep the right hand within 2 mm and 0.02 rad of its grasp, the left hand backs off 10 cm while the right waits, then the right, the bar is placed where it was let go of, and a plan holding nothing starts from the end. A pick, a carry holding the bar and a place run end to end, each from where the one before ends. A start off its grasp, a second pose 4 mm off, a second hand that is the pick's own or out of range, second-hand grasps fewer or more than the pick's, a pair whose holds lock a joint at two values or whose costs add past a finite one, a place started with a hand off its grasp, and a `handover` of what two hands hold are input errors. A start that holds the bar with the right hand 1.5 mm along two axes from the grasp its hold names, within a pin, is followed whole at the default precision and at half of it, the right hand keeping its place in the left's frame to one and a half precisions at 1 kHz. On two Pandas with a third hand on the left arm's fourth link, a path of that hand while the other two hold the bar is an input error, and is taken with the joints it shares held. A hold that names a hand twice, a hand the robot lacks, a grasp that is not finite or unit, or a hand of a device that holds something in it already is an input error from IK and from a plan. A pick by one hand and one by two in one call, and places of what each holds, come to what each comes to alone, and an idle configuration that puts the second hand's joints past their limits changes nothing of a place by two. With both hands at the bar and the left holding it alone, the right hand's straight move back and its plan home stop where they start, against the held bar; with the right hand's links among those the bar may touch (`Held::touch_links`) both go through, on every device, and a link the robot lacks is an input error.
- **Touches for what a hand comes to hold (`Touch::held`):** a world uploaded to the device that holds nothing lets what a hand comes to hold touch an obstacle. IK, a plan and a straight move holding a cube that meets a slab end at rest on it in that world alone, bit for bit as a device holding the cube solves it. A robot of 64 links keeps the touch in a word of its own. Two hands' touches in a world or an upload, a hand the robot lacks, and a problem holding in the other hand are input errors.
- **Many holds in one call:** fifteen hundred ways to hold a box, each set down at either of two turns, are placed in one call; five thousand finger openings, two grasps at each, are picked by in one; four thousand ways to hold a cube are planned in one; and two thousand ways to hold a bar are passed to the other arm in one; each as it is alone.
- **Handing over:** a bar passed from one Panda to the other has transits that keep clear of it, checked at 1 kHz, finer than the planner checks them.
- **Turns (`turn`):** on every device, a knob turned a quarter turn in place by either grasp from above ends with the hand turned about its own z axis by the angle and the knob turned with it (`placed`). The motions join from the transit to the move away, which goes back along the hand's z axis from where the turn ended; plans come quickest first, and each grasp alone moves alike. A lever swung 60 degrees about a hinge 10 cm from the grasp keeps the hand within 0.55 of the precision of the arc and under the tool speed, and a cap unscrewed half a turn along its thread keeps the hand on the helix to within the precision. Where the configuration IK finds nearest the start cannot make a turn whole, the turn is made from the first configuration, nearest the start first, that can.
- **What a turn meets:** the hand holds what it turns. A post only the swinging arm reaches stops the turn, saying how far it got, and named in `support` lets it by; a cap on its bottle turns only with the bottle named; with `stays`, nothing checks the obstacle the fingers turn in. A post the fingers meet partway round stops the turn at `TaskStep::Turn` as colliding with the post, saying how far it turned, and the move away is checked against the object where the turn leaves it. Of 36 grasps out of reach and two that are not, one plan that will do (`enough`) is the first of the two; a knob with a post where an open finger comes down turns only with the fingers locked 3 cm apart; and a grasp whose rotation is 1.0008 of unit turns in place. 64 knobs in one call each give the result they give alone. An angle of 0, not finite or of more waypoints than can be held, a screw not unit or not finite, a support that is the object, an object that is a distance grid or not in the world, no approach, no grasps and no plans enough are input errors naming the task.

## Grasps

- **Grasps of shapes:** grasps of a box, ball, cylinder and capsule lie `depth` inside the surface, face into it and close on no more than the gripper's capacity; a distance grid has none. Over a floor, the open fingers of a gripper that grasps less than it opens stand its loaded gap apart, the lower finger kept over the floor at that spread. `place_poses` turns a box onto itself 2 or 4 ways and a round object `turns`. Malformed tasks and options, starts past the limits, rotations that are not unit and a place on a device that already holds the object are input errors.
- **Over a floor:** of a 2.5 cm cube with a floor and fingertips 12 mm past the frame, the four grasps from above hold it as deep as keeps the fingertips at the floor and the eight from the sides close level at the full depth; none closes upright, whose lower open finger would be in the table, and none comes from below. A floor over the cube leaves none and says so, and a box wider than the opening says how wide. A Panda picks a cube narrower than twice its fingertips' reach only with grasps kept off the table. A bar over a plate, as a drawer's handle, is gripped tilted about it, held as far out as keeps the lower open finger over the floor, and every such grasp picks it on each device.
- **The gripper (`Robot::gripper`):** the Panda's jaws slide where the calibrated stroke moves both fingers' spheres half the change in gap each, and not with one finger closed, past a stop, with a revolving mimic, a skewed axis or a torso lock that moves. A capacity past the loaded gap, a hand the robot lacks and a pad friction that is not finite and positive are refused. Openings turn into finger joints and back between the closed and the loaded gap, exact at both ends, for the Panda relocked as a TIAGo's hand and for a hinged jaw as the SO-101's, which does not slide and whose narrowing is refused by name. `grasps_on` takes the widths and the friction from the gripper, whatever the options say.
- **Grasps of a surface (`grasps_on`):** on surfaces sampled from shapes whose grasps are known, the grasps are those and no others. A box is grasped across each side that fits; a bowl too wide to span, across its wall all around its rim; two leaning faces, along the line that splits their normals where that lies inside both friction cones. Sides farther apart than the gripper grasps, a sheet 1 mm thick, a surface with nothing seen behind it and patches with something else between them give none. The hand's spheres and its way in stay clear of what stands beside the object and of a ledge of the object itself, and the frame, the fingertips and the lower open finger stay over a floor. Every pair comes from every turn both ways round where the hand is clear, from above first. A box on a table seen by two cameras is grasped across the sides between them, clear of the table, and readings of the robot are not surfaces. Grasps are the same on one thread and many, alone and in a batch, and on every device. An overlap of zero or less, a floor that is not finite and flags for some of a surface's points are input errors.
- **A leaning wall:** a flared bowl's inner wall, leaning 27°, is closed on level by fingers with a friction of 2, the hand straight down across the rim all around and the open hand out of the bowl. Fingers with a friction of 0.3 get no level grasp.
- **Walls seen from one side (`SurfaceGraspOptions::shell`):** a flared bowl's rim seen from above alone has no grasp without a shell, and with one of 1.5 cm is grasped all around, each grasp closing from the inner wall seen to a point outside the bowl within the shell, the open hand clear of the whole bowl. A box seen from in front and over it is grasped across the whole of it with a shell of 8 cm, and seen from above alone has none. By default a wall is taken as thick as the fingers open, and a thicker shell gives what one at the opening does. The grasps without a shell come first and unchanged, a shell adds grasps only where no camera faced the wall, and a second look from the same place, joined to the first, takes none of them away. `from_depth` records the camera each point was seen from and `from_points` the place; `join` keeps them and marks the points of a side that did not say as unknown. A shell that is not a positive thickness and places for some points only are input errors.
- **Narrower fingers (`SurfaceGraspOptions::narrow`):** every grasp comes in at the opening the rule gives the Panda relocked at each sixteenth of the opening, way in included: farthest from any at which it is in what is not the object's, then the most room, then the widest. With walls farther than the fingers could reach, and with nothing near, every grasp is as without the option, at the full opening. A box too long to close along, 3 cm from a wall as tall, has no grasp with the fingers open; with `narrow` it has, at the box's width, and a pick whose grasps lock the fingers there plans on every device. Grasps with `narrow` do not depend on the threads, the batch or the device.
- **Moments (`Grasp::moment`):** on the grasps `grasps_on` finds on a bar 2.5 cm wide and two plates, a grasp's moment is 2.25 cm a newton across the bar about an upright axis through its middle (friction 0.5, patches 5 mm); about an axis off the grips' middle, the way round that gives less; along the closing line, friction alone, from each fingertip's slide at its distance from the line and its twist; and alike either way round the line.
- **Near a point (`SurfaceGraspOptions::near`):** on a bar 16 cm long, the grasps are those without the point, by the same turns from above in the same order, the first at the point and within each turn nearest the point first. `None` leaves every grasp of `examples/surface_grasps.rs` as it was, to the bit. A point that is not finite is an input error.
- **First touch (`SurfaceGraspOptions::first_touch`, on by default):** held to a flared bowl's true shape, its unseen outside too, within each turn of each lot the grasps whose fingers meet the bowl more than two patches' radius past their own come after all whose fingers meet it no more than a surface's noise past, and so of plates with a ledge beside one. The same grasps come without it, in the order they came, from above still before a turn to either side.

## Rests and falls

- **Rests (`rests_on`):** on supports whose rests are known, rests stand where the rule says and nowhere else. A box rests on a table at each of the eight turns, clear of what is not the support, and hangs past an edge only as far as its weight stays over what it stands on with the tipping asked for; a post too narrow holds nothing. A basket holds a can inside its walls, and on its rim only where two walls meet. A can laid along two bars rolls in between and rests touching both, and one laid across a slope rolls down to a lip and rests against it. A tile on a slope rests short of the friction's angle less the tipping and not past it, with exact normals, noisy ones and a board read by a rendered camera. A ball rests on a rim under it and on three posts, and rolls off half a rim and off a table.
- **Balance:** every rest on the racks holds by a balance of forces and torques written apart from the library's. The closed form for one flat face agrees with the general balance, and a flat bottom on a top measured in strips tips as far as on one face. The first rests are the steadiest and spread over the support. `place` sets down what was found on a rendered scene.
- **Seen from above (`seen_from_above_holds`, on by default):** a support seen only from below holds nothing up. A board with a lip read at a slant by a camera above it, noisy enough that some of its fitted normals face down, holds the box in far more places with the option on and where it was seen from known than with the option off or without where it was seen from.
- **Looking closer (`look_closer`, on by default):** an upright bottle on a slope of 30 degrees with a lip 1 cm high and wide, where the grid finds no rest, rests against the lip near the spot over the lip's top nearest the middle of the support, every rest holding by the balance written apart and tipping as far as asked; without looking closer it has none. Told where the caller would have it, the object rests within a spacing of the spot nearest the point or of the point. Where the grid finds rests, as on a table bare or among blocks, every rest stands on a spot of the grid, the same as without looking closer. Looking closer starts at the spot where the object tipped as set down nearest the point given, not at one it rolled to. More closer spots than a call takes and more cells than a surface is read in are input errors.
- **Why none (`rest_failures`):** `Unsupported` where nothing flagged lies under the object or the support was seen only from below; `Unheld` on a slope steeper than the friction, the support's push within a degree of its normal; `Tips` on a post too narrow, at the steadiest place, within half a degree of the closed form; `Blocked` by a wall within the clearance, ahead of `Tips`; and none where it rests. Rests that are not one list a problem, and problems `rests_on` refuses, are input errors.
- **Falls (`falls_into`):** a can over a pen with walls taller than its middle is let go at every spot where it fits, its bottom the clearance over the walls, at every turn, the middle first, and lands 8 cm under the rim. Walls lower than its middle, a gap the can fits through, a corner too narrow for it, a floor no camera saw and a table give none, while a hole no camera saw in the pen's floor is let go over as deep. A block already in the pen is landed on and nothing is let go over it, and beside a wall or a block standing taller than the rest the can is let go the clearance over it. A tilted box's drop is measured with its shape grown by the clearance along its own axes. Over a round bowl it barely fits, a box falls only by looking closer, as by default, over the axis first at every turn.
- **Near a point:** with a point to put them near, rests and falls come nearest it first in x and y, each costing that distance, those as near in the order they came.
- **Everywhere alike:** rests, their failures and falls are the same on one thread and many, alone and in a batch, and on every device, by default and with neither option. Malformed surfaces, objects and options are input errors, and `falls_into` checks its input as `rests_on` does.
- **In MuJoCo:** `scripts/validate_rests.py` lets go of each rest of `examples/surface_rests.rs` in MuJoCo, on the support as a height field: 250 of 250 tried on the table, 250 of 250 in the basket, 60 of 60 cans between the bars, 148 of 150 on the rack and 224 of 224 upright bottles against the lip with a top stay; those on the rack that move lie at the very end of the support. Of the 822 trays across the bars, 249 of 250 tried stay.

## Perception

- **Grids from depth:** on every device, depth images from an 8×8 time-of-flight array and from a 640×480 camera both reproduce the table under them, follow each occlusion rule (below the table: solid, free, or solid within a band and free past it), and leave unobserved space free. The GPU builds exactly the CPU's grids from point clouds and maps under every occlusion rule, and classifies a 640×480 image's voxels and fuses it into a map with at most 0.05% of voxels differing. A depth that is zero, negative or not finite is no reading, and a surface reads the same on one thread and on many.
- **Maps:** a fused map keeps the table, holds a ball seen through twice and clears it the third time, leaves space never observed to the rule given, and takes no hits from readings beyond its edge.
- **The robot's mask:** masked out of a camera's image, the Panda's spheres read free in grids and maps alike, while a box in front of the arm stays solid. What only the arm hides is solid under `Occlusion::Occupied` and free under `OccupiedExceptRobotShadow`, in one image and in a map; what the box hides stays solid. A camera on the Panda's palm keeps the floor it sees past its fingers, while every reading of the arm is left out. A held box named in the mask is left out and the space it fills is free, where unnamed it is an obstacle in the hand; fingers shut on a small object are the robot's with the hold's locked values.
- **Filtered images (`DepthImage::filtered`):** a reading with a nearer surface on one side and a farther one straight across is left out, and both surfaces are kept up to the edge, as are a slit and a wire one pixel wide. A wall turned 78 degrees keeps every reading, one turned 82 loses those with a neighbour on both sides, and keeps them where the caller allows 85. A step of 2.9 cm 2 m off stays and one of 3.15 cm goes at two deviations of 1 cm of noise; a wall with 2 cm of noise loses none of its readings where the filter is told of the noise. A map fused from the filtered image of a block whose edge pixels read halfway down its side holds no point in mid-air beside it. Options that would leave every reading in and an image whose depths do not form rows are input errors.
- **Shapes in the mask (`RobotMask::with_shapes`):** a mask given shapes flags exactly the readings within the margin of one, as a check of every pixel against every shape says, for boxes, balls, cylinders and capsules turned, a table, a floor far larger than the view and walls beside and behind the camera, at margins of each coefficient; a distance grid given as a shape flags the readings within the margin of the grid as it is turned. With a table and a block given, one look fuses nothing of them, and what only the block hides is never observed. Once the block is carried away, its place and what it hid are freed with nothing said to the map, and a second block no shape explains is occupied at its third look. A reading the caller flags itself is left out too. The voxels a mask frees in its shapes are those of testing every voxel, but for voxels within 1e-5 m of the reach. A mask of another image, a margin below zero or not a number, and a shape that is none are input errors.
- **A band behind the flags (`RobotMask::with_band`):** the mask flags exactly the readings that lie behind a thing of a flagged reading within the band, as a check of every unflagged reading against every flagged reading of the band and every thing of the mask says, on every device and on one thread; readings in front of each thing are kept. A box 1 cm high on a table given as a shape, and a wall half of which is one, keep every reading of what is not a shape. Without a band, a block whose outline reads halfway to what lies behind it leaves voxels occupied in mid-air beside it; with a band of one pixel or five none are, and every reading moved nearer stays, which is what the band gives up. A margin below zero or not a number and a mask of another image are input errors.
- **Which shape a point lies on (`sdf::on_shapes`):** the nearest of the shapes it lies within its reach of, as the shapes' own distances say, and of two as near the first, for points in an image's rows and scattered through the room, at every reach from none to unbounded; the same on one thread, on many and with the points in another order. A point with a coordinate that is not a number lies on none. On a device of one thread it runs on that thread and starts none.
- **Marking space (`free`, `clear`):** a caller's `free` marks exactly the voxels within the margin of a box, a ball, a cylinder, a capsule and a grid, each turned, and `clear` makes them never observed again. In a fused scene a ball marked free is gone from the grid, one more look brings it back, and cleared it is solid or free as the grid is told; space seen through three times stays as it was when marked free, and one reading does not fill it.
- **Parts of a map:** a part holds the map's voxels that reach into its region and none else. Its grid of a tray with a block in it, never-observed space solid, is free under the table beside it where the whole map's grid is solid, reaches the padding past the tray, and never reads farther from the tray than the tray is. Counts add up to the region's voxels, a part takes no images, what a caller marks in a part stays in its region, and a region half off the map is never observed there. A region whose part would hold more than 2^26 points, or whose diagonal would reach 4,096 voxels, is refused.
- **Occupied voxels (`occupied`):** as many points as the map counts, each on the map's points, in their order, more likely occupied than not and within a voxel diagonal of what the camera saw; a new map has none, and a voxel at even odds is not among them. A part's are the map's within its reach of the region.
- **One image decides (`Weighing::Latest`):** on every device, a block's top that five looks saw empty is occupied after one look at the block, and one filled five times is freed by one look through it, where weighed as evidence it takes three looks to fill and stays occupied. A block outside the deciding image and one hidden behind a board held over it keep what they were. Every voxel holding a reading of a table seen at a grazing angle is occupied under either weighing, and the never-observed voxels and the grids built from them after a look are the same under either. The GPU's map has the CPU's occupancy but for at most one voxel in 2,000, what the devices' classification is held to.
- **What a fuse visits:** a fuse on the CPU visits only the voxels it can change: a row's span holds every voxel whose middle projects into the image, for cameras inside, beside and outside a map, images from one pixel to 640×480, focal lengths from a fifth of their width to three times it, and a map 10 km from the origin whose voxels are finer than a float's spacing there. Every voxel more than a voxel outside the view keeps its state unless the mask frees it, and voxels holding a reading whose middles project past the image's edge take their hits.

## Robots

- **Kinematics:** URDF forward kinematics matches Franka's published DH parameters to 1e-5. The 2F-85's link poses match an independent composition of its URDF with mimic joints applied; its collision gradient matches finite differences, and the GPU agrees with the CPU. Mimic limits intersect into the leader's range and velocity.
- **Loading:** collision-model files round-trip, SRDF pairs stop being checked, and `package://` paths resolve. A binary STL whose header starts with "solid", as CAD exporters write it, loads as its ASCII twin does. The UR5e, SO-101 and Panda (with fitted spheres) each plan 12 of 12 tabletop motions on the CPU and the GPU. A Panda with fitted spheres, whose base spheres reach into the table it stands on, is collision-free on it and plans on every device, while a pin through its elbow still collides.
- **Fitted spheres:** fitted spheres contain independently sampled link surfaces, and fitting is deterministic. They keep every link of the SO-101, a box with a fin 0.15 mm thick and a stand's boxes within its tolerance where the budget allows, and the SO-101's jaws held to 1 mm reach less far at each doubling of the budget from 128 to 512. Where the budget reaches the stand's tolerances but cannot hold them, 512 spheres reach less far than 384 and keep to the budget. The model's `source` gives the largest of each link's reach over its own tolerance. On two wide thin plates, no link reaches farther than twice its tolerance times the scale the fit reports.
- **Spheres, tips and reach:** `Robot::spheres(q)` is the collision model placed at the links' poses, and a hand's `tip` is its spheres' farthest reach along its frame's z axis. `Robot::reach` bounds every sphere over 2,000 random configurations climbed toward the farthest on six robots, among them a planar base level and on a slope, and stays within 12% of the farthest found.
- **`Robot::qualify`:** on the SO-101 it reports every link with geometry, its largest overhang equal to the fit's own account to its tenth of a millimeter. Halving one link's spheres leaves over 30% of its surface uncovered, and moving a sphere 5 cm off a link raises its overhang by more than 2 cm. With the jaws held to 2 mm (`sphere_tolerances`), at 256 spheres, they reach less far than any other link and than they did.
- **A limit on overhang (`SphereOptions::max_overhang`):** a stand's boxes fitted at 0, 2 and 20 mm have every sphere within the limit of its box; `qualify` reports each link's overhang within the limit and a `gap` no less than, and within a centimeter of, what the box's corners and its faces' middles lie outside the spheres. A given model is held as a fitted one: a sphere past the limit, one centered outside, one whose radius is not a number and one on a link without geometry are refused by link and index with how far they reach. Inside a closed mesh is where the surface winds around, for faces given both ways, boxes that share a face and boxes that overlap. A box with a face missing is refused with its open edges, fitted or given, and so is one with a face given twice. A plate 0.05 mm thick under a limit of zero is refused by name and covered at 2 mm. A limit that is negative or not finite, and a budget of zero, are input errors from `load`, `from_urdf` and `assemble`.
- **Held shapes under a limit:** a box is covered whole within 3 mm at 512 spheres, fitted within it at 64 with some of it left out, and inside it at zero; a capsule's spheres stay on its axis within 1 mm; a plate's layer is within 4 mm; a ball is its own sphere. A sheet too thin is refused by name, and so are a sheet and a disc of no thickness at a limit of zero, which at 2 mm are covered. A plate held within 4 mm slides past a neighbor 6 mm from its side, where spheres fitted within 12 mm read it as touching.
- **Held objects' spheres:** held boxes, discs, rods and capsules are covered without fitting: a plate 14 cm across, with 256 spheres to spend, by one layer of at most 160 that hold every point of it and reach no more than the tolerance past it; a rod and a capsule by spheres along their axes. A held ball is exactly one sphere, and a cylinder held upright and tilted has the same spheres, tilted. A held object's spheres reach its tolerance whatever its budget: a bowl takes the same spheres at budgets of 1, 64, 256 and 1,024, and a box and a capsule 1.21 m long reach no more than 5 mm past them. Every point of a bowl, a thin slab, a sheet, a long bar, a disc and a mug lies inside a sphere, and every sphere's radius and its center's signed distance sum to no more than the tolerance. Sphere options per hold (`Held::spheres`) apply per problem in one call, on every device; a handover's taker holds the object with the giver's, and options that cannot cover anything are an input error naming the problem.
- **Attaching:** an attached box moves with the hand, collides with an obstacle between the fingers that the bare hand misses, and collides with the fingers unless they are touch links. Collision gradients through it match finite differences, and detaching restores the robot exactly. Devices made with `with_robot` plan around the box in worlds uploaded to the original device, and see it exactly as a device made for the held robot does, on the CPU and the GPU. Attaching outside a rayon pool leaves the calling thread out of rayon. Attaching to an unknown link, under a taken name, with an unknown touch link, or a shape whose size is not finite or whose rotation is not a unit quaternion is an input error.
- **Relocking:** relocked joints move their links, mimic joints' links included, to where a robot loaded at the new values has them. A device made with `with_robot` for a relocked Panda checks collisions as one made for the Panda loaded there, against worlds uploaded before, on the CPU and the GPU, and the GPU reuses the kernels it built. A joint locked when the collision model was fitted stays at its value: relocking it is refused, and so is loading the model with it free or locked elsewhere, through a model saved and loaded again and two arms assembled from it too. A NaN lock value is refused at load and on relock.
- **Touch links:** named finger links replace the links below the palm, and a block against the SO-101's fixed jaw, part of its palm's link, is touched only with them named. `World::always_touching` finds the SO-101's link that turns just above its base on its table, and not a block it rests in by default or a slab just under the table; plans from rest fail `StartCollides` without the touch and solve with it. A turntable's table, on a continuous joint, is found in a slab level with it.
- **MJCF:** Menagerie's Panda matches our URDF Panda link for link to 1e-5. Menagerie's UR5e matches the UR5e URDF up to constant per-link frame offsets (within 3 mm; Menagerie rounds a few dimensions), and plans like the others. A handwritten model pins MuJoCo's conventions against hand-composed transforms: degrees by default, intrinsic Euler sequences, `axisangle`, `xyaxes`, `zaxis`, joint anchors, several joints per body, includes, default classes and `fromto`. Scene meshes collide as their convex hulls.
- **OpenUSD:** handwritten fixtures pin UsdPhysics conventions against hand-composed transforms: Y-up centimeters, a payload and a variant fallback; flat and nested bodies, `localPos1` ≠ 0, a joint authored child to parent; both mimic schemas, an instanced collider, and unauthored primitive sizes. newton-assets' UR5e matches the Menagerie MJCF it was converted from exactly; their 2F-85 mimics its driver and fits spheres to mesh colliders read from a binary layer. The Franka converted from our URDF matches it to 1e-5, with identical self-collision results under the same collision model. Scene meshes collide as `physics:approximation` says. `scripts/validate_usd.py` rebuilds every fixture's kinematics with Pixar's `usd-core` and agrees with batchplan to within 6e-6.

## Demonstrations and export

- **Pick-and-place:** on each device, 6 of 6 tabletop tasks succeed. The gripper closes once, across the box's narrower side, and moves gradually. The box is held at the grasp point without slipping and set down within 3 mm of the place pose. The arm never touches the scene, the lifted box clears it, and velocities agree with positions. A ledge just over the box's far end stops its lift, a ledge over where its far end goes stops the lowering, and a low slab where it would stand stops the release, each at its step through `pick` and `place`. Boxes the wrist cannot set down as asked are set down turned half way round, each episode's goal and box where its own task says. Over 64 tasks, the joints travel under 13.5 rad in the median episode.
- **Handovers:** on each device, at least 6 of 8 handovers between two Pandas succeed, the giver reaching past a post. Each gripper closes once and opens once, giver then taker. The block rides without slipping in the giver's hand and then the taker's, and ends within 3 mm of its place. - **Exporters:** the `.npy` export round-trips trajectories, padding, labels, grippers, carried poses and tasks, and the LeRobot export writes consistent v3.0 metadata. A 1,500-episode export with 1 MB files spreads frames and episode metadata over several files; each episode row names its own file and the file holding its frames, and the statistics match the frames. Tasks are indexed per frame, the gripper is the last state dimension, and a carried box moves in the environment state frame by frame. Exports write each grid once, and LeRobot's environment state describes a grid by its box. Both refuse to overwrite an existing dataset.

## Embedding

- **Threads:** a one-thread CPU device starts exactly one thread and no others while it plans. With rayon's global pool kept busy for a second, the GPU device plans at once, on threads of its own.
- **Allocations:** `plan`, `rrt::connect` and `shortcut::shortcut` build each search on the thread that runs it: per problem, the calling thread allocates 3, 4 and 1 times, for the results' copies of the problems.
- **Time budgets:** a 1 ms time budget returns within one more chunk of work than the budget, on the CPU and the GPU, and searches stop at the budget too. Without a budget, two runs give identical paths. These tests run one at a time in `tests/budget.rs`, since other tests' threads beside them swing wall-clock times past the slack.
- **Errors:** errors have the documented kinds: a malformed batch is `Input`, an unknown adapter `Gpu`, a bad file `Load` with its path, an unsafe trajectory `Unsafe`. Adapters below the required limits are rejected with the reason, and an unknown adapter name is a clear error.

## Running the tests

```bash
BATCHPLAN_REQUIRE_GPU=1 cargo test --release                       # fail instead of skipping GPU tests without a GPU
BATCHPLAN_REQUIRE_GPU=1 cargo test --release --features lerobot,usd
cargo test --release --no-default-features                         # the CPU-only build
```

Without `BATCHPLAN_REQUIRE_GPU`, tests that need a GPU skip silently when no adapter exists. `scripts/validate_lerobot.py` and `scripts/validate_usd.py` check exports and USD loading against the reference Python packages (`lerobot`, Pixar's `usd-core`) in a virtual environment. The first also loads datasets with the camera videos `scripts/replay_mujoco.py` renders.
